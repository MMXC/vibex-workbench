各位好，今天我们来看 MOD-build-panel 模块的 spec 说明。

这是一个前端模块，负责在 UI 层调用后端的 make 命令来执行 lint-specs、validate、generate 等操作。

目前处于 proposal 阶段，owner 是 hermes，我们来详细分析一下这个模块的设计意图和实现差距。

📊 当前模块分析 (As-Is)

🔧 模块职责

Build Panel 负责在 UI 层触发后端的 make 命令执行，并将结果以视觉化方式呈现给用户。

🔗 依赖边界

只负责"调用"和"展示结果"，不负责自动修复。执行在 backend 进程（WORKSPACE_ROOT 环境变量注入）。

📡 接口设计

POST /api/workspace/run-make
{target: 'lint-specs' | 'validate' | 'generate'}

⚠️ 异常处理

成功：绿色提示 "✅ lint-specs 通过"
失败：红色浮层，显示错误摘要（前 500 字符）

IO Contract 核心定义

类型内容
Input用户点击「校验 Spec」或「生成代码」按钮
Outputstdout/stderr 前 500 字符 + exit code
Boundary只负责调用和展示，不负责自动修复

先来看当前模块的 As-Is 分析。

这个模块的职责很清晰：用户点击按钮 → 调用 API → backend 执行 make → 返回结果 → UI 展示。

注意这里的边界：前端只负责调用和展示，不做自动修复。这意味着如果 lint 失败，用户需要手动去改代码。

接口设计是 POST /api/workspace/run-make，参数是 target，可以是 lint-specs、validate 或 generate。

异常处理上，成功显示绿色提示，失败显示红色浮层并截取前 500 字符。

🔧 优化方向与风险

优化方向建议

📌 优化 1：实时输出流

当前方案截断至 500 字符，建议考虑 SSE 或 WebSocket 实现实时输出流

复杂度：中 收益：高

📌 优化 2：点击跳转定位

失败时支持点击错误行号跳转到对应文件位置

复杂度：高 收益：高

📌 优化 3：历史记录

记录最近 N 次执行历史，支持快速回溯

复杂度：低 收益：中

📌 优化 4：批量执行

支持同时发起多个 target 的执行

复杂度：中 收益：中

风险分析

🔴 高
Backend API 未就绪
/api/workspace/run-make 接口不存在或未正确处理 WORKSPACE_ROOT 环境变量
🟡 中
Make 命令执行超时
大型仓库的 lint/generate 可能耗时较长，需要超时机制
🟡 中
输出截断丢失关键信息
500 字符可能不足以展示长错误堆栈

这一页我们讨论优化方向和风险。

优化方面，建议四个方向：1) 实时输出流（用 SSE/WebSocket）；2) 点击跳转定位；3) 历史记录；4) 批量执行。

风险方面，最高风险是 backend API 还没就绪；其次是执行超时和输出截断可能丢失关键信息。

建议在 MVP 阶段先做基础的调用-展示能力，后续再迭代这些高级特性。

验收标准

若集成测试失败：拆分为更小的 PR 进行验证

若 production 问题：Feature Flag 禁用 Build Panel，保留手动入口
