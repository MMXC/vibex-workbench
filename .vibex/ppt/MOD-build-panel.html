决策 Decision

⚖️ 决策：方案对比与选择

维度方案A: 纯前端实现方案B: 前后端协同方案C: 暂不实现
描述 前端轮询获取状态，本地渲染 WebSocket 实时推送，后端管理状态 保持现状，依赖命令行
优点 简单快速，无需后端改动 实时性好，状态一致 零投入，无风险
缺点 轮询开销，状态可能不一致 后端改动量大 用户体验差，无可观测性
成本 低 高 零
推荐 ✅ Phase 1 考虑 Phase 2 ❌ 不选
🎯 推荐方案: 方案A（纯前端）
  • Phase 1 实现所有 P1 功能
  • 使用现有 prototype 架构
  • 通过 polling 实现流式效果
  • 验收后评估是否需要方案B
🔄 切换条件
  • 用户反馈延迟 > 2s 时考虑方案B
  • 多命令并发场景增多时考虑方案B
  • Phase 1 验收通过后评估 Phase 2
decision 6 / 8
决策页。Why 方案A：最小成本实现核心价值。Why not 方案B：后端改动量大，当前阶段不划算。Why not 方案C：用户反馈强烈需要改进。切换条件：Phase 1 验收时重新评估。
执行计划 Execution

🚀 执行：里程碑与验收

📅 Phase 1: P1 功能实现
  • 负责人: 前端开发
  • 周期: 1 周
  • 里程碑: error_details + stdout 渲染
  • 验收标准:
    • lint-specs 结果完整显示
    • validate 错误可折叠展开
    • generate 输出分色显示
📅 Phase 2: P2 功能增强
  • 负责人: 前端开发 + 后端（评估）
  • 周期: 1 周
  • 里程碑: streaming_log + 状态过滤
  • 验收标准:
    • 长命令实时滚动
    • Tab 切换延迟 < 100ms
🔙 回滚策略
  • Phase 1 回滚：使用现有的 progress + exit_code 基础显示
  • 功能开关：可通过 config 禁用高级功能
  • 灰度发布：先对内部用户开放，监控无异常后全量
📊 风险缓解
  • 风险1（流式输出性能）：限制最大日志行数，滚动丢弃旧数据
  • 风险2（内存占用）：超过 1000 行时提示导出
  • 风险3（并发状态）：使用 Map 管理，按 command_id 隔离
execution plan 7 / 8
执行页。Why 2 周分两个 Phase：每阶段可验证可回滚，降低风险。回滚策略：保留基础显示作为 fallback。关键：验收标准必须可量化。
