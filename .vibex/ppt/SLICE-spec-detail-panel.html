状态矩阵 Validate Bar 四态 + specPath 变化

📊 状态矩阵 — Validate Bar 与 specPath 切换

场景 UI 状态 触发方式 预期行为 错误处理
specPath 变化 loading Monaco 清空 用户点击 tree 节点 加载内容 → 展示 读取失败时显示错误，不清空 Monaco
Validate 通过 pass 绿条 Ctrl+S 或 Validate 按钮 "✓ Valid" + 耗时 N/A
Validate 失败 fail 红条 同上 "✗ Invalid" + 错误列表 点击错误 → 跳转行号
Validate 警告 warning 黄条 部分字段缺失 "⚠ Warning" + 警告数 允许继续，但需关注
Validate 运行中 running 灰条 + 旋转 点击 Validate "Validating..." 超时显示提示
读取失败 error 红字 spec 文件不存在 错误提示 Monaco 内容保留
💡 设计决策：读取失败时不清空 Monaco 当前内容，避免用户编辑数据丢失。这是保护用户体验的关键决策。

边界演示 · Constraints 验收口径 · 禁止事项

🚧 边界演示 — 明确职责边界与触发方式

✅ 本 Slice 负责

  • SpecDetailPanel 整体布局（header + editor + footer）
  • 元信息侧栏渲染（LevelBadge / StatusChip / Name / Parent/Children Chips）
  • Validate Bar UI（按钮 + 状态 + 错误列表展示）
  • Monaco Editor 集成与布局适配
  • Ctrl+S 保存快捷键绑定
  • History 按钮事件 emit
  • 错误列表点击 → Monaco 跳转行号

⛔ 明确禁止（其他模块负责）

  • Monaco Editor 内部实现 — FEAT-spec-write
  • validate 验证逻辑 — Go agent
  • git 操作（commit/push/pull）
  • 文件浏览器（tree 组件）— 外部传入 specPath
  • wailsReadSpecFile / wailsWriteSpecFile 底层实现

🔗 边界协议 — 与外部模块的接口约定

Props: specPath: string, specContent: string
Events: save({path, content}) | validate({path}) | openHistory({path})
HTTP Fallback: GET /api/workspace/specs/read | POST /api/workspace/specs/write | POST /api/spec/validate

决策页 推荐方案 · 备选 · 取舍 · 风险

⚖️ 方案决策 — Why / Why-Not

决策点 ✅ 推荐方案 ❌ 备选 / 为什么不选 前提条件 切换条件
Validate 逻辑归属 Go agent 负责，本 slice 只展示结果 自实现 validate → 增加开发成本，且与 Go agent 重复 Go agent validate API 可用 Go agent API 延迟 > 5s 或不可用
Monaco 集成 复用 FEAT-spec-write 的 MonacoEditor.svelte 自封装 Monaco → 重复造轮子，且维护成本高 MonacoEditor.svelte 已集成 MonacoEditor 不满足布局需求
读取失败处理 不清空 Monaco 当前内容 清空 → 用户编辑数据丢失，体验差 需要保留编辑状态 产品策略改为"失败即清空"
HTTP Fallback browser dev 模式 fallback 到 HTTP 纯 Wails → dev 模式无法调试；纯 HTTP → 生产环境不稳定 dev 模式有 HTTP server dev 模式也走 Wails
错误列表交互 点击错误 → Monaco 跳转行号 + 高亮 只展示错误 → 用户需要手动搜索，效率低 Monaco 支持 jumpToLine API Monaco 行跳转 API 变更
💡 核心决策原则：复用优先、边界清晰、用户体验优先。每一个"不做什么"都是经过权衡的主动选择。

待完善问题清单 可复制 · 用于与 agent 继续对话

📋 后续讨论问题清单

以下问题用于在详情抽屉继续和 agent 对话完善 spec：

  • specPath 变化时，加载动画的时长阈值是多少？（何时显示 loading spinner）
  • 错误列表最大展示条数限制是多少？超出如何处理？
  • Monaco 编辑器是否需要语法高亮配置（YAML schema 校验）？
  • Validate Bar 是否需要支持"自动 validate"开关？
  • History 按钮展开的 SpecHistoryPanel 位置是侧边还是底部？
  • Parent/Children Chips 点击后的行为是路由跳转还是展开 tree 节点？
  • SpecName 可编辑时，是否需要同步更新 Monaco 内容区的 name 字段？
  • 大量 spec 文件时，是否需要实现虚拟滚动（virtual scroll）？
  • Validate 结果是否需要持久化到本地（localStorage）？
  • Ctrl+S 保存失败时，toast 提示的时长和样式规范是什么？
  • 是否需要支持撤销/重做（undo/redo）功能？
  • spec 内容变更后，是否需要通知其他模块（如 tree 刷新）？

🎯 优先高收益问题（建议优先讨论）

  1. 错误列表条数限制 — 影响布局稳定性
  2. Parent/Children Chips 交互行为 — 影响用户体验一致性
  3. Validate 自动开关 — 影响交互流程
