本页介绍今天要讲解的 L4 Feature Spec。这是一个关于 Agent 推荐 Spec 写入前的用户确认协议的规格说明。 目标受众包括：CTO（关注架构约束）、开发（实现路径）、测试（验证策略）、用户（体验收益）。
功能目标 CTO · 架构决策

核心目标：约束 Agent 写盘边界

🔒

强制用户确认

任何 agent 推荐都不能替代用户确认，未确认前 specs/write 不被调用

📁

规范目录路径

target_dir 必须来自 FEAT-spec-graph-expansion.level_rules，禁止 agent 自行拼接

⚡

Prototype Gate 对齐

涉及 prototype 物料的写盘须过 UI workflow gate，避免静默写盘

Why 做：防止 agent 污染 spec 仓库，确保 spec-first 流程可控
FEAT-agent-spec-write-protocol 2/9
为什么要做这个协议？因为当前的 agent 协作流程存在静默写盘的风险。 如果不约束，agent 可能直接覆盖已有的 spec，或者写到错误的目录层级。 这个协议本质上是给 agent 的"写权限"加了一道必须经过用户确认的门。

FEAT-agent-spec-write-protocol 3/9
这是 create-child-spec 的完整流程。第3步是关键的 gate：用户必须明确确认。 如果用户取消，不调用任何写盘 API，git status 不会出现新文件。 第5步的 make validate 是必须的，不能跳过。如果失败，要按 validation-and-failure.md 分类处理。
约束规则 测试 · 验证策略

三大约束 + C3 补充

ID 约束名称 核心规则 验证方式
C1 Explicit confirmation 未确认前 specs/write 不被调用 拦截所有写盘请求直到用户确认
C2 Canonical directory 禁止 agent 自行拼接 specs/{level}/ 校验 target_dir 必须来自 level_rules
C3 UI workflow gate prototype 写盘须过 ui_workflow_run.decision gate_blocked + 失败码分类

C3 失败码分类

intent_incomplete ui_spec_incomplete acceptance_missing confirm_required
FEAT-agent-spec-write-protocol 4/9
测试需要重点关注这三个约束的验证路径。 C1 的验证点：确认前没有任何写盘操作，可以监控 API 调用日志。 C2 的验证点：检查 agent 是否正确使用 level_rules 而不是自行拼接路径。 C3 的验证点：prototype 相关写盘的 gate 状态，需要模拟 ui_workflow_run.decision 非 passed 的场景。
用户故事 用户 · 体验收益

US-1: 自举用户的核心诉求

作为 自举用户
我想要 agent 帮我起草下一层 spec，但写盘前必须确认
以便 既能加速 spec-first，也不会污染仓库

验收条件 (AC)

AC-1
Given: 用户未确认 agent 草稿 When: create-child-spec 流程进行中 Then: 系统不得写入任何 spec 文件
AC-2
Given: 用户确认草稿 When: 系统调用 specs/write Then: 写入路径必须位于 target_dir 且 parent 等于 parent_name
AC-3
Given: 写入完成 When: 系统运行 make validate Then: 结果按失败分类显示在 agent 线程和 Problems/Output 区域
FEAT-agent-spec-write-protocol 5/9
这是从用户视角看这个 feature 的价值。用户不需要懂技术细节，只需要知道： 1. agent 会先给一个预览，而不是直接写盘 2. 我可以修改或取消，不用担心污染仓库 3. 写盘后会自动校验，结果会展示给我 三个 AC 覆盖了完整的用户路径，从确认前、确认后、到校验结果展示。
测试场景 测试 · 覆盖盲区

关键测试场景

TC-1

用户取消澄清

Given: agent 已生成 L4 spec 草稿 When: 用户点击取消 Then: 不调用 specs/write
✅ 验证: git status 不出现新 YAML
TC-2

写盘后校验失败

Given: agent 草稿 parent 写错 When: 用户确认写盘 Then: make validate 失败并显示 parent_not_found
✅ 验证: 线程保留草稿，提示下一步修复
TC-3

C3: prototype gate 拦截

Given: 写盘请求含 prototype 物料 When: ui_workflow_run.decision 非 passed Then: 归类为 gate_blocked + 返回失败码
✅ 验证: 响应 body 含 gate_failure.code 数组
FEAT-agent-spec-write-protocol 6/9
测试需要覆盖这三个核心场景。 TC-1 是 Happy Path 的取消分支，验证隔离性。 TC-2 是失败恢复路径，验证草稿保留机制。 TC-3 是 C3 的新增场景，验证 prototype gate 的拦截逻辑。 回归风险：主要担心的是确认前后的状态一致性，以及校验失败时的用户体验。
决策点 CTO · 最终拍板

方案 A vs 方案 B vs 方案 C

维度 方案 A (推荐)
强约束确认协议		 方案 B
宽松确认协议		 方案 C
静默写盘 (不选)
用户控制力 ✅ 完全控制 ⚠️ 部分控制 ❌ 无控制
污染风险 ✅ 零风险 ⚠️ 低风险 ❌ 高风险
实现复杂度 ⚠️ 中等 ✅ 低 ✅ 极低
与现有系统兼容性 ✅ 良好 ✅ 良好 ⚠️ 需重构
prototype gate 对齐 ✅ 完整对齐 ⚠️ 部分对齐 ❌ 不对齐
推荐方案 A：强约束确认协议

Why: 零污染 + 完整 prototype gate 对齐 + spec-first 流程可控

Why Not B: 缺少 C3 prototype gate 对齐，长期存在静默写盘风险

Why Not C: 明确违反 spec-first 原则，不可接受

FEAT-agent-spec-write-protocol 7/9
这是决策页，需要 CTO 做最终拍板。 方案 A 是推荐的，强约束 + C3 对齐。 方案 B 为什么不选？因为缺少 C3 prototype gate 对齐，长期会有静默写盘风险。 方案 C 为什么不选？直接违反 spec-first 原则，不考虑。 成本：实现中等复杂度，需要改写现有的 specs/write 调用点。 风险：用户可能觉得确认流程繁琐，但这是必要的护栏。
