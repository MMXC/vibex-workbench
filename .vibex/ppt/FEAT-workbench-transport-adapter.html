L4 Feature Spec

Workbench 传输适配层

HTTP / SSE / WS · Wails

📦 FEAT-workbench-transport-adapter 👤 Owner: hermes 📅 2026-05-09

架构契约：在模块侧收敛传输选型与基址；
功能侧只消费门面，禁止散落拼接 URL。

欢迎各位。今天我们来讲一个横切面（cross-cutting）的架构设计——Workbench 传输适配层。 这个 spec 解决的是：桌面壳内嵌前端同时存在多种传输通道，如何避免功能代码重复维护端口、基址和分支逻辑。 先看封面：这是 L4 级别，聚焦"功能级落地差距"。
功能目标 CTO · 战略层

🎯 核心目标：统一传输入口

  • 收敛协议选型 → 模块层统一判断 Wails/浏览器/HTTP fallback
  • 消除重复代码 → 功能代码禁止复制 SSE_URL 常量块
  • 双轨基址隔离 → workspaceApiBase ≠ agentApiBase，日志可区分
  • 类型安全门面 → workspace.readSpec、agent.postChat 等签名稳定
  • 可测可验证 → grep CI + code review 双门禁
💡 边界：不替换 Agent/Go 服务协议形态；不合并 SSE 与 WS 为单一通道
CTO 关注的是架构风险和资源投入。这个 spec 的价值主张： 1. 减少技术债——不再有散落的 VITE_SSE_URL 硬编码 2. 提高可维护性——传输策略只在一处维护 3. 降低跨层 bug 风险——功能代码不关心当前是 Wails 还是 Vite 代理 约束也很清晰：不做协议合并，只做前端收敛。这降低了实施风险。

边界演示 Developer · 规则层

🚧 三大约束规则

T1

收敛于模块

传输策略、环境变量、Wails 探测只允许在 transport*.ts 中

❌ 禁止：业务目录出现 http://localhost:33338

T2

发散于功能

各 FEAT 只调用门面：workspace.readSpec、agent.postChat

❌ 禁止：组件内拼接完整 URL

T3

双轨基址

workspaceApiBase ≠ agentApiBase

❌ 禁止：混用或日志无法区分轨道

✅ 验证方式：grep CI（可选）+ code review 双门禁
三个约束规则是 spec 的核心： T1 防止硬编码扩散——所有传输策略必须在一处 T2 强制门面模式——功能代码只消费接口，不知道底层实现 T3 强制基址分离——日志里能区分"卡在同源"还是"卡在 Agent 端口" 触发方式：如果代码 review 发现业务目录有裸 http://localhost:33338，就是违规。

决策点 All · 决策层

⚖️ 方案对比与决策

✅ 推荐

渐进式迁移

先完成 P1/P2 门面，再逐步迁移调用点

  • ✓ 风险可控，每阶段可回滚
  • ✓ 不破坏现有功能
  • ✓ 便于 code review
成本：中等 风险：低
⚡ 备选

大爆炸迁移

一次性全量替换所有调用点

  • ✓ 快速达到目标状态
  • ✗ 风险集中，回滚困难
  • ✗ 需要同步修改多个 FEAT
  • ✗ 测试覆盖压力大
成本：高 风险：高
🔑 Why Not 大爆炸：当前 P1/P2 验证门未通过；多个依赖 spec（MOD-ide-chrome、FEAT-workspace-selector）未同步
决策页给出了两个方案的对比： 推荐方案是渐进式迁移——风险可控，每个阶段可以独立合并和回滚 备选方案是大爆炸迁移——虽然快，但风险集中 为什么选渐进式？ 1. wails-filesystem 的验证门尚未通过，不能盲目切通道 2. 多个依赖 spec 未同步，贸然迁移会破坏现有功能 3. 当前已有 DONE-T1 到 DONE-T5 的部分实现，需要接续而非推翻 前提条件：如果 P2 的 wails-filesystem 验证通过，且依赖 spec 同步更新，可以考虑加速 P3/P4。
