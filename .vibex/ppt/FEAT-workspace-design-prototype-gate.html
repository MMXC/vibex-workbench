功能目标

功能目标 — 核心能力矩阵

🎯 目标 1：双轨维护机制

  • 每个仓库根目录维护 DESIGN.md
  • 每个模块维护 prototypes/ 物料目录
  • spec 与 prototype 修改均经显式确认后写盘
  • 禁止静默覆盖历史版本

🎯 目标 2：原型槽策略条

  • 工作台提供可操作的策略条（ActionStrip）
  • 支持快速查看/切换原型状态
  • 支持从原型深链到 spec 详情抽屉
  • 支持 spec 变更触发原型刷新提示
why（为何做）：当前工作区缺少设计意图的持久化存储，spec 与 prototype 分散管理，导致设计与实现脱节、历史追溯困难。

状态矩阵

状态矩阵 — 三种原型场景

场景触发条件UI 表现ActionStrip 状态
✅ 有原型 prototypes/ 存在且有内容 显示缩略图 + 版本号 + 最后修改时间 绿色状态条，可点击展开
📭 空原型 目录存在但无文件 空状态提示 + "生成原型" 按钮 灰色状态条 + 创建入口
⏳ Loading 原型加载中 / 网络延迟 骨架屏 + loading 动画 脉冲动画表示加载中
❌ 错误态 文件损坏 / 路径不存在 / 无权限 错误提示 + 重试按钮 红色状态条 + 警告图标
why（为何矩阵重要）：原型槽是用户高频交互入口，状态不一致会直接导致信任崩塌；loading/error/empty 三态必须完整覆盖。

边界演示

边界条件与约束规则

🔒 规则 1：禁止静默覆盖

  • DESIGN.md 修改必须 diff 展示
  • prototype 修改必须版本快照
  • 用户点击确认后才写盘
触发：修改文件 → 弹出确认对话框

🔒 规则 2：跨仓库隔离

  • 每个仓库独立 DESIGN.md
  • 不允许跨仓库引用 prototype
  • 原型路径基于 workspace.root
触发：切换工作区 → 刷新 ActionStrip

🔒 规则 3：版本回滚

  • 每次写盘生成版本快照
  • 支持回滚到任意历史版本
  • 回滚操作需要二次确认
触发：详情抽屉 → 历史版本 → 回滚
why-not（为何不用自动保存）：自动保存虽有便利性，但设计文档和原型是高价值资产，静默覆盖风险极高；显式确认是必要的摩擦成本。

决策与执行

方案决策 — 推荐 vs 备选

维度推荐方案 A备选方案 B不选理由
存储位置 每仓库根目录 DESIGN.md 统一 .vibex/design/ 集中存储 集中存储不便于 Git 管理与代码同生命周期
确认时机 修改后立即确认写盘 批量确认（定时/退出时） 批量确认增加数据丢失风险，即时确认更安全
版本快照 每次写盘生成快照 + diff 仅保留最新版本 无快照则无法回溯，高风险场景必须保留历史
原型关联 spec.id → prototype 一对一映射 多原型可关联同一 spec 多对多增加歧义，一对一更清晰可追溯
成本估算：开发 3 天 · 测试 2 天 · 文档 1 天 · 总工时 ≈ 6 人天
风险等级：中（依赖文件系统 I/O，无网络依赖）
