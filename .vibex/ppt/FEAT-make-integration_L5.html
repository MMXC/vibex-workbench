Wails Binding Guard 约束

SLICE-wails-binding-guard 规则：Wails 环境仅允许 window.go.main.App.*，禁止 Wails 内 fallback。 菜单触发链必须遵循：runtime events → business binding → 严格判定，禁止混合使用。

Forbidden 边界

  • ✗ 禁止在前端直接执行 make 命令
  • ✗ 禁止忽略 exit code（make 失败必须展示错误）
  • ✗ 禁止跳过 workspace_root 验证

方案决策 Decision: Why & Why Not

方案对比与决策

维度方案A: SSE 推送方案B: WebSocket方案C: HTTP 轮询
实时性 ✓ 高（服务端推送） ✓ 高（双向通道） △ 低（延迟取决于轮询间隔）
实现复杂度 ✓ 中等（标准 SSE） △ 高（连接管理复杂） ✓ 低（无状态轮询）
资源占用 ✓ 单向，低开销 △ 需要维护长连接 ✗ 频繁请求增加负载
适用场景 make 输出流、log tail 需要交互的实时场景 简单轮询场景
推荐 ✅ 采纳 备选（未来交互需求） 不选（不符合实时需求）

Why / Why Not 决策说明

✅ 选 SSE

  • Why: make 输出是单向流，SSE 天然匹配
  • Why: HTTP/1.1 兼容性好，无需 WebSocket 握手
  • 前提: Wails SSE API 可用

✗ 不选 WebSocket

  • Why Not: 过度设计，单向流不需要双向
  • 切换条件: 未来需要前端→后端实时交互

问题清单 Q&A for Spec Refinement

可复制的问题清单

复制以下问题，在详情抽屉与 agent 对话以完善 spec：

  • make lint-specs / generate / validate 这三个 targets 的实际输出格式是什么？需要解析到什么粒度？
  • SSE stream 路径 /workspace/{threadId}/output 中 threadId 的来源和生命周期？
  • workspace_root 验证是前端做还是后端做？验证失败时返回什么错误码？
  • Wails binding guard 中 runtime events 和 business binding 的具体边界在哪里？
  • make 执行超时如何处理？是否有 timeout 配置？默认多久？
  • Output Tab 的滚动策略：自动滚动到底部还是用户可自由滚动后暂停自动滚动？
  • exit code 非 0 时，Problems Tab 的更新逻辑是追加还是全量替换？
  • 多个 make 并发执行时（如同时点 lint-specs 和 generate），如何处理输出隔离？
  • make 过程中前端断开 SSE 连接，后端是否需要取消正在执行的 make 进程？
  • "重新运行"按钮是否需要保留上一次执行的 target 参数？
  • 是否需要支持用户自定义 make targets？还是只支持 spec 定义的这三个？
  • Makefile 依赖的外部工具（如 node、go）未安装时，错误展示是否需要提示安装命令？
💡 使用建议: 选择 3~5 个与当前实现最相关的问题先确认，优先级排序后逐个推动 spec 完善。
