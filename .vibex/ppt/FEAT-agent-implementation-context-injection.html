功能目标

what & why

🎯 核心目标

  • 在 agent 实现 spec 前，自动组装并注入上下文摘要
  • 摘要包含：历史 checkpoint、失败分类、下一步建议
  • 避免重复读错文件、重跑无效方案

📦 产出物

  • 一段 bounded context block
  • 标记 stale_journal / memory_only
  • 标记 known_failures / must_not_repeat
Why: 当前 agent 实现新 spec 时完全"盲启动"，无法感知历史 journal 和 memplace 经验，导致重复踩坑。

current state · no context injection

🔍 现状证据

维度现状问题
journal 读取不自动读取agent 不知道上次失败原因
memplace 命中不触发提示相似失败可能重演
spec 优先级无显式规则新旧信息冲突时无处理
上下文大小无限制可能塞入过多历史日志
Why Not 直接套用: 当前无任何注入机制，agent 完全依赖实时搜索，无法复用历史决策。

注入策略与偏差分析

policy & gap analysis

📋 注入上限 (max_items)

类型上限
current_spec_checkpoints5
related_spec_checkpoints3
memory_hits5

🔀 优先级顺序

  1. current spec
  2. current L5 parent
  3. direct child L5
  4. sibling L5 (shared files)
  5. memplace/memlace hits

📐 偏差分析

偏差 A

无 journal 时依赖 memplace → 标记 memory_only，降低置信度

偏差 B

摘要超出限制 → 按 priority_order 截断，保留高优先级

约束 C1

Bounded injection：不把完整 journal 直接注入

约束 C2

Spec wins：当前 spec 与摘要冲突时，spec 优先

决策页

decision · CTO & Dev

方案描述优势风险决策
推荐：受限注入 max_items 限制 + priority_order + spec wins 防止上下文爆炸；保证当前 spec 权威性 可能遗漏低优先级历史 ✓ 采用
备选：无限注入 全量 journal + memplace 摘要 不遗漏任何历史 上下文过长，LLM 稀释关键信息 ✗ 放弃
备选：仅 journal 忽略 memplace，只读 journal 简化实现 无 journal 时完全无上下文 ✗ 放弃

👔 CTO

控制上下文体积，避免 token 浪费；保证 spec 优先，避免 agent 被旧信息误导。

💻 开发

实现简单：读取 → 截断 → 注入；可调试性强，标记清晰。

⚠️ 风险

journal 过期时标记 stale；memplace 置信度不足时标记 memory_only。

验证与风险

testing · user · risk

🧪 测试场景

TC-1: 同一 L5 二次实现

Given: L5 有 journal，记录 build_error

When: agent 重新开始实现

Then: 摘要包含 build_error、涉及文件、避免重复动作

TC-2: memplace 命中但 journal 不存在

Given: memplace 有摘要，无 journal

When: agent 组装上下文

Then: 标记 memory_only，降低置信度

👥 用户/业务视角

  • 加速交付：agent 不重复踩坑，迭代更快
  • 质量提升：避免已知失败重演
  • 透明度：显式标记数据来源（journal vs memory）
Why Not 跳过验证: 无测试会导致边界情况（空 journal、超长摘要）未覆盖。

🚨 风险矩阵

风险概率影响缓解
过期 journal 覆盖当前 spec低高C2: spec wins 强制约束
上下文超出 LLM 窗口中中C1: bounded injection
memplace 误判高置信度低中memory_only 标记 + 降权
