功能目标 Why / What / Success

为什么要做 — 业务价值

🎯 目标（What）
  • 在 IDE 标题栏菜单（文件/编辑/视图…）点击时触发事件
  • 支持 open 与 close 两种状态
  • 暴露菜单项 ID / 标签，供业务层监听与响应
  • 为"菜单驱动"的工作流自动化奠定事件基础
💡 价值（Why）
  • 打通 UI 交互层 → 业务逻辑层的事件总线
  • 支持插件/脚本订阅菜单行为，实现自定义扩展
  • 为"菜单点击 → 动作执行 → 日志记录"提供原子化钩子
✅ 成功标准
  • 点击任意标题栏菜单项 → 控制台输出 EVT_titlebar_menu_click（含 menu_id）
  • 菜单关闭时 → 控制台输出 EVT_titlebar_menu_close
  • 测试用例覆盖 open / close / error 三种路径

边界演示 Constraints · Edge Cases

边界场景与触发条件

⚡ 核心边界（spec 定义）
  • 点击菜单外区域 → 触发 EVT_titlebar_menu_close，reason=outside
  • 按 Esc 键 → 触发 close，reason=escape
  • 点击菜单项后关闭 → 触发 close，reason=select
  • 窗口失焦 → 触发 close，reason=blur（建议补充）
🛡️ 防御边界
  • 重复点击同一菜单按钮 → toggle（先关后开）
  • 菜单打开时切 tab → close，reason=blur
  • 右键非标题栏菜单 → 不触发（仅标题栏）
  • 禁用状态菜单项 → 仍触发 click 但不响应 action
📋 Constraints 现状

当前 constraints.rules 为空数组。需由开发者在实现阶段补充具体规则（如：菜单层级限制、点击防抖、事件冷却时间）。

风险与验证 Risk · Verification · Rollback

风险、验证与回滚

⚠️ 风险项
  • 风险 1：菜单 UI 组件不存在 → 事件无触发载体
    对策：先建 UI 组件，再接入事件
  • 风险 2：Wails 事件名冲突 → 覆盖已有事件
    对策：命名空间隔离 vibex.menu.*
  • 风险 3：频繁点击导致事件风暴 → 影响性能
    对策：防抖 100ms + 事件冷却
🔬 验证方式
  • DevTools Console：window.vibex.on('menu.*', console.log)
  • Vitest：mock 菜单点击 → 断言事件派发
  • Playwright：点击菜单 → 等待控制台事件日志
↩️ 回滚策略
  • Git revert 前端 commit（事件代码独立成 commit）
  • 回滚后菜单降级为纯 UI 无事件状态
  • Wails 事件总线解注册：window.vibex.off('menu.*')
